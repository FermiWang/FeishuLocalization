# 详细会议记录并行整理可行性与落地说明

日期：2026-08-27

## 结论

并行整理可行，但“把单任务队列直接改成 8 个线程”不能解决现有超时。原实现同时存在三个瓶颈：应用只有一个执行器；只要 vLLM 有任意运行中请求就拒绝发起新阶段；聊天接口使用非流式响应，长篇记录在整篇生成完成前收不到响应体，因而可能触发 900 秒读取超时。

落地采用以下组合，而不是单独提高线程数：

1. 会议应用默认使用 6 个可恢复执行器，配置允许 1–8；
2. 214 的模型调度容量按 8 控制，默认给每日洞察及其他调用保留 2 个名额；
3. 详细记录模型响应改用 OpenAI 兼容 SSE 流式接收；
4. 模型满载、健康探测暂时失败、流式连接超时或中断时，保留数据库断点后重排队，不立即提交重复推理，也不把会议永久标记为失败；
5. FunASR 仍保持单路执行，避免多份录音同时加载语音模型造成 179 内存压力；文字整理任务不受该单路限制。
6. 详细会议记录按协议允许的最高优先级 `-9223372036854775808` 提交；vLLM 数值越低越优先，JSON 与 `X-Vllm-Priority` 请求头同时携带该值。

## 核查证据

- `processing_jobs` 由 SQLite WAL、`busy_timeout` 和 `BEGIN IMMEDIATE` 原子领取任务，多个执行器不会领取同一个任务。
- 原处理器只有一个后台线程；原模型准入条件是运行数或等待数大于零即退避，因此无法利用 214 的并发能力。
- 214 暴露精确模型 `Qwen3.8-27B-FP8`，vLLM 运行数和等待数可从 `/metrics` 读取。
- 2026-08-27 使用不含业务数据的 128-token 请求实测了 `stream=true`：3.4 秒内收到 13 个 SSE 数据块及 `[DONE]`，证明现有 OpenAI 兼容接口支持流式输出。
- 现场曾同时出现 179、214 从当前工作机均不可达的局域网连接超时。应用因此将网络/健康探测失败纳入可恢复状态；发布验收仍必须在局域网恢复后完成，不能用单元测试替代线上健康证明。

## 调度边界

| 层级 | 默认值 | 边界与理由 |
| --- | ---: | --- |
| 214 模型调度容量 | 8 | 用户确认的服务上限；超过时由 vLLM 排队，应用在提交前也检查运行数与等待数 |
| 会议整理执行器 | 6 | 保留 2 个模型名额，降低每日洞察或其他模型调用被会议任务完全占满的风险 |
| 会议模型请求优先级 | -9223372036854775808 | vLLM 64 位整数范围的最低值，即协议允许的最高优先级；214 已用该值实测确认启用 priority 调度 |
| 服务端等待队列保护 | 16 | 运行 8 路满载时仍允许会议请求进入优先队列；只在等待异常堆积时退回本地断点 |
| FunASR 执行器 | 1 | 语音模型内存开销大；只序列化转写阶段，不序列化后续文本整理 |
| 流式读取无数据超时 | 900 秒 | 由“等待整篇完成的总等待”变为“连续无数据”超时 |
| 临时故障重排队 | 30 秒 | 保留已完成片段抽取断点，避免紧密重试和重复占用模型 |

环境变量 `MEETING_MAX_PARALLEL_JOBS` 可在 1–8 调整。若线上观察到延迟、KV cache、等待队列或每日洞察受影响，可先降为 4；紧急降级可设为 1，数据库和 API 无需回滚或迁移。

## 恢复与一致性

每个执行器通过同一原子领取接口取得不同任务。分块抽取完成后立即保存 `checkpoint_json`；服务重启会把 `running`、`waiting` 恢复为 `queued`。流式连接中断不覆盖断点，不立即重发同一个尚可能在服务端运行的请求。最终记录仍通过现有不可变修订、输入哈希复核和乐观锁写入，因此并行执行不会允许旧输入覆盖新来源或人工修订。

本次改动不增加数据库表或列，回滚不需要数据库逆迁移。

## 发布验收

发布必须依次完成：

1. 全量测试和会议应用测试通过；
2. 提交并推送后备份 179 的代码、SQLite 和上传目录；
3. 部署并重启，验证首页、`/api/system/model`、精确模型身份和 6 个活动执行器；
4. 使用隔离数据目录同时启动至少 3 个合成文字会议，观察模型运行数大于 1、任务 ID 不重复、全部完成且生成 DOCX；
5. 重启一次隔离实例，确认运行中任务恢复排队；
6. 检查生产数据库中原超时任务从已有分块断点继续，而不是从零开始；
7. 检查 179 与 214 日志无持续错误，再结束临时验收实例并移除其临时数据。
